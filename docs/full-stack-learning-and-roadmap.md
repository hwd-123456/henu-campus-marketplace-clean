# 全栈构建教学与 CampusCart 下一步路线

本文用当前项目说明一个网站怎样从前端、后端、数据库一路构建到可交付版本，并把已完成内容和待办事项对应起来。

## 1. 一套完整网站的请求链路

```text
React 页面
  ↓ fetch + JSON + Authorization Bearer token
FastAPI 路由 /api/v1/*
  ↓ Pydantic 校验 + 权限依赖
MongoDB users/products/orders/errands/...
  ↓
JSON 响应 → React 状态 → 页面更新
```

每增加一个功能，都要同时完成四件事：

1. 前端页面和加载、空状态、错误状态。
2. 后端请求模型、路由、响应模型和权限规则。
3. 数据库文档结构、索引和初始化数据。
4. 至少一个接口测试和一条手动验收路径。

## 2. 推荐学习顺序

### 第一步：React 和前端工程

- 学 JSX、组件、props、state、Effect 和表单。
- 学路由和“公开页面 / 登录后页面”的边界。
- 学请求状态：`loading`、`success`、`empty`、`error`。
- 本项目入口是 `frontend/src/App.jsx`，页面组件在 `frontend/src/components/`，接口封装在 `frontend/src/services/api.js`。

推荐资料：[React 官方安装与项目指南](https://react.dev/learn/installation)、[React 官方 Quick Start](https://react.dev/learn)。

### 第二步：FastAPI 后端

- 用 Pydantic 定义输入和输出模型。
- 用路由拆分资源，例如商品、订单、跑腿、私信。
- 用依赖注入读取当前用户。
- 用 `/docs` 检查 OpenAPI 文档和接口请求体。

本项目入口是 `backend/app/main.py`，路由在 `backend/app/routes/`，模型在 `backend/app/models/`。

### 第三步：MongoDB 数据层

- 先确定每个集合的字段合同。
- 对查询、排序和唯一字段建立索引。
- 在应用启动时建立连接，在关闭时释放连接。
- 不把数据库密码或 JWT 密钥写进代码或提交到 Git。

推荐资料：[MongoDB 官方 FastAPI + PyMongo 教程](https://www.mongodb.com/docs/languages/python/pymongo-driver/current/integrations/fastapi-integration/)。项目目前使用异步 Motor；新功能应沿用现有异步访问方式，并统一处理数据库不可用的情况。

### 第四步：认证和安全

正确流程应是：

```text
注册 → 校验校园邮箱和密码 → 保存密码哈希
登录 → 查询已注册用户 → 校验密码 → 签发有过期时间的 token
请求受保护接口 → 校验 token → 得到当前用户
退出 → 清理前端 token，并使服务端会话失效或自然过期
```

推荐资料：[FastAPI OAuth2 + JWT + 密码哈希教程](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/)。JWT 是签名令牌，不是加密文本；不要把密码放入 token 或 localStorage。

## 4. 对照教程后发现的关键缺口

### A. 认证规则需要先修

当前认证代码存在“数据库不可用时本地回退”和“首次登录自动创建用户”的兼容逻辑。它适合演示页面，但不符合“先注册、密码正确才能登录”的产品要求。

应继续做：

- 已注册用户才能登录；不存在的邮箱返回统一的登录失败提示。
- 删除演示密码绕过逻辑。
- 注册时校验邮箱、密码长度、学号格式和重复账号。
- 前端显示登录进度、失败原因和重试按钮。
- 只缓存 token 和非敏感用户摘要，禁止缓存密码。
- 生产环境使用环境变量提供随机 JWT 密钥。

### B. 数据库环境要可重复

当前项目依赖 MongoDB，但组员本地容易出现 `localhost:27017` 未启动。应继续做：

- 提供 Docker Compose 的 MongoDB 开发环境，或统一使用 MongoDB Atlas 测试库。
- 写 `.env.example`，实际 `.env` 加入 `.gitignore`。
- 启动时明确显示数据库连接成功/失败。
- 为 `users.email`、`products.campus`、`errands.status`、消息会话字段建立索引。

### C. 测试要分层

- 单元测试：密码校验、字段校验、状态机，不依赖真实数据库。
- 接口测试：使用专用测试 MongoDB，测试注册、登录、权限和 CRUD。
- 前端验收：登录、发布商品、跑腿接单、私信、退出后回访。
- CI：每次 PR 自动执行前端 build、Python compile、pytest。

### D. 部署要补齐

- 前端部署到静态托管平台，配置 `VITE_API_URL`。
- 后端部署到服务平台，配置 MongoDB URI、JWT 密钥、CORS 白名单。
- 生产环境只允许 HTTPS，Cookie 和 token 策略统一。
- 增加 `/health`、日志、错误追踪和备份策略。

## 5. 五个交付包建议

### 交付包 1：认证和登录体验

负责注册、登录、退出、token 恢复、登录加载状态和错误提示。

验收：未登录可浏览公开页面；点击收藏、发布、购物车、私信时弹登录框；密码错误不能登录；刷新页面后有效会话仍在。

### 交付包 2：数据库与安全配置

负责 `.env.example`、MongoDB 启动说明、索引、JWT 密钥、敏感配置检查。

验收：新电脑按文档能启动数据库；仓库中没有真实密钥；数据库断开时页面给出明确提示。

### 交付包 3：商品交易闭环

负责商品列表、详情、收藏、购物车、下单、订单状态和库存一致性。

验收：库存不足不能下单；刷新后购物车和订单仍能恢复；未登录操作会进入登录流程。

### 交付包 4：跑腿和站内沟通

负责跑腿发布/接单/完成，以及会话列表、消息发送、未读状态和空状态。

验收：跑腿状态只能 `open → claimed → completed`；创建者不能接自己的单；私信需要登录且失败可重试。

### 交付包 5：测试、部署和交付文档

负责 pytest、前端构建、CI、部署说明、演示账号和最终验收清单。

验收：新成员按 README 能启动；PR 检查通过；能用演示账号完成一次浏览、登录、交易和跑腿流程。

## 6. 推荐的实际推进顺序

1. 先完成交付包 1，解决登录规则和登录体验。
2. 再完成交付包 2，固定每个人的数据库和环境变量。
3. 并行完成交付包 3、4，前端统一调用接口，不再把 localStorage 当正式数据源。
4. 最后完成交付包 5，把启动和验收流程固化到 CI。

每个包都从 `main` 创建分支，提交小 PR，并在 PR 描述中写：改了哪些文件、如何启动、如何验证、已知限制。
